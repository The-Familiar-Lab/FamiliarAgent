# Tool verification on Mac and Ubuntu

Checked on **2026-10-09** against the final installed v0.16.2 runtimes on Mac and Ubuntu. Both expose **26 catalog tools, 19 dedicated original-tool adapters and 94 actions**; seven catalog entries are native providers or desktop/history entry points rather than dedicated external-tool adapters. A catalog entry, an installed executable, a successful login and a completed task are separate states.

These checks used isolated projects and original executables, services, records and model responses. They do not establish that every provider, orchestration mode or private runtime checkpoint is portable. The original tool retains its execution loop, permissions and native sessions. FamiliarAgent connects supported inputs, results, history references and shared resources.

**Verified** below means the stated workflow actually ran. **Authentication needed** means installation or discovery worked but the model workflow remains blocked. Representative original workflows passed for **17 of the 19 dedicated adapters**; Aider and OpenHarness remain authentication-gated. Final code checks passed **1,832 automated tests** and the release build. These automated checks are separate from the native workflow evidence below.

The final read-only catalog reported 25 installed entries on Mac and 23 on Ubuntu. Mac Firetower uses a remote Linux control plane; Ubuntu has no local Antigravity IDE, ChatGPT or VS Code desktop app. These installation counts do not imply that every installed tool is signed in.

## Result composition and Discord

The real two-host chain passed: **Ubuntu Goose result → Mac native Codex input/response → Ubuntu Goose continuation**, in one Familiar logical session. Two new model requests were used for this check. This proves that specific selected-result path; it does not prove unrestricted private-state transfer between all 26 tools.

Automatic result delivery is restricted to prompt actions. A shell command, terminal keystroke or file-data action is not treated as an LLM prompt. `submitted` or `accepted` means the original endpoint acknowledged delivery; completed work must be established from its native result/status. Shared MCP access depends on the tool's supported launch hooks and the selected resource permissions.

Discord has a separate existing human-message roundtrip proof. The earlier read-only audit rechecked the original human input, expected native response, delivered receipt and the bound agent's then-`idle` state. Saved channel/role restrictions and the original token reference were preserved. The final installed app was then reconnected with **Connect Discord** and its UI reported **connected**. The last read-only check still resolved the saved binding and prior delivered receipt; after deployment the bound native agent reported `closed`, not an active turn. The original connector was preserved. A fresh human-message roundtrip after this build is **not yet verified**: the attempted UI submission did not appear in the latest channel messages. The read-only audits sent no messages and changed no settings or processes.

## Installer provenance and pins

- Original release archives are selected by OS/architecture and checked against recorded SHA-256 values. The infrastructure installer extracts only the intended regular executable members into a staged private installation, refuses unrelated existing binaries and verifies an existing version before reusing it. Sources are the official releases of [Firetower](https://github.com/firetower-cloud/firetower/releases/tag/firetower-v0.44.0), [Skulk](https://github.com/frantufro/skulk/releases/tag/v0.7.1), [bssh](https://github.com/lablup/bssh/releases/tag/v3.0.1), [Coder](https://github.com/coder/coder/releases/tag/v2.36.7) and [JuiceFS](https://github.com/juicedata/juicefs/releases/tag/v1.4.1). Firetower's Linux control-plane binary comes from its pinned official container layer; it is not a newly implemented server.
- Source-built integrations verify the exact upstream Git commit before their native dependency/build commands. Examples include [Hydra](https://github.com/jpdlr/hydra), [Codey](https://github.com/its-ahoh/codey), [wshobson/agents](https://github.com/wshobson/agents) and [Docker Skills](https://github.com/docker/skills). Binary integrations such as Orca, Codeg and Alethe use pinned original release artifacts. The checked-in [integration recipes](../plugins/familiar-workspace/server/integrated-tools/setup-recipes.ts) contain exact revisions and digests.
- Goose and Claude Squad use reviewed original installer scripts with explicit release versions. Cursor and Antigravity use their official vendor installer URLs with reviewed script hashes. A script-hash pin is **not** a guarantee that every downstream vendor-selected binary version is fixed. If those script bytes change, installation fails its integrity check until the recipe is reviewed. See [native installer recipes](../plugins/familiar-workspace/server/tool-catalog/installers.ts).
- Pinning is not uniform across package-registry installs. Pullboard specifies its package version; some original npm/Python tools follow the version selected by their package installer. superharness additionally specifies its required Claude SDK dependency. The [catalog](../plugins/familiar-workspace/server/tool-catalog/catalog.ts) records these distinctions; this document does not claim a fully locked third-party dependency graph.
- Electron-based setup explicitly runs the installer in Node mode and checks the expected executable after exit. An exit code of zero without the executable is an error. Account stores stay with the original tools; credentials are not transferred between hosts.

The underlying verification summaries cover infrastructure, integrated systems, native harnesses, providers, editor/history reads and the cross-tool chain. Private test paths, account identifiers, tokens and conversation bodies are intentionally omitted here. Code regression tests cover failure and boundary behavior separately from these native workflow checks. For usage, see [setup and composition](setup-and-composition.md) and [native tool actions](native-tool-actions.md).
